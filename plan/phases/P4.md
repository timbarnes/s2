# P4. Assignment, `letrec` and internal definitions

Done 2026-10-10. `set!` works on local, captured and global variables;
internal `define`s, `letrec`, `letrec*` and named `let` work, with mutually
recursive local procedures. A variable is boxed only when it has to be.

```
s2> (dis '(define (make-counter) (let ((n 0)) (lambda () (set! n (+ n 1)) n))))
template make-counter  arity 0
   0  Fixnum 0
   1  MakeBox 0        ; n
   2  LocalRef 0       ; n
   3  MakeClosure k0   ; #<template>
   4  Return
template (lambda)  arity 0  free 1
   0  FreeRef 0        ; n        the box, for BoxSet
   1  GlobalRef k0     ; +
   2  FreeRef 0        ; n
   3  BoxRef                      its contents
   4  Fixnum 1
   5  Call 2
   6  BoxSet
   ...
```

## Decisions

**D6 completed: flat closures plus assignment conversion** (03 §7). A
closure copies values, so a variable must live in a box, a one-field heap
object, whenever a copied value could be wrong. `boxed_variables` finds
two cases:

1. **Assigned and captured.** `set!` on the variable anywhere, and a
   reference from a lambda other than the one that binds it. Without a
   box, the closure's copy and the stack slot would diverge after the
   `set!`.
2. **Referenced before initialisation.** A `letrec` variable used in its
   own init or an earlier one. A recursive procedure is the usual case: its
   closure is made while the variable is still undefined, so the closure
   has to capture the box, which is filled afterwards.

Everything else stays where P2 put it:

- an assigned variable that isn't captured is a stack slot, written by
  `LocalSet`;
- a captured variable that is never assigned is copied by value;
- a `letrec` variable used only after its init (in later inits or the
  body) is a stack slot, assigned once by `LocalSet`.

`tests/golden/set.dis` shows all three. The analysis is one walk over the
whole top-level form. It records which lambda binds each variable and
which `letrec` variables are still pending (their init hasn't been walked
yet).

**The second rule is narrower than the roadmap's.** 03 §7 said that the
`letrec` assignment "makes recursive closures boxed", which would treat
every `letrec` variable as assigned, and box every captured one. That's
stricter than needed. The only `letrec` variables that need boxes are the
ones referenced while still pending. `parity` in `tests/golden/letrec.dis`
shows the difference:

```scheme
(define (parity n)
  (define (even? n) (if (= n 0) #t (odd? (- n 1))))
  (define (odd? n) (if (= n 0) #f (even? (- n 1))))
  (even? n))
```

- `even?`'s closure is made while `odd?` is pending, so it must capture
  `odd?`'s box: `odd?` is boxed.
- `odd?`'s closure is made after `even?` is set, so it can copy `even?`'s
  value: `even?` is a plain slot, and `odd?`'s body calls it with no
  `BoxRef`.

This is a small step towards P10's *Fixing Letrec*, which would remove
the remaining box.

**Instructions.** As the roadmap listed, as stack operations:

- `MakeBox i` replaces local `i`'s value with a box holding it. It is
  emitted where a boxed variable is bound: at procedure entry for a
  parameter, after the inits of a `let`.
- `BoxRef` pops a box and pushes its contents. `BoxSet` pops a value and
  a box.
- `LocalSet i` and `GlobalSet k` pop into a slot or a binding cell.
- `Undefined` pushes the undefined value, which a `letrec` variable starts
  with.

Each assignment leaves nothing on the stack, and codegen then pushes
`Unspecified` as the value of the `set!` expression. In a body, that's
immediately popped: `BoxSet; Unspecified; Pop`. P10's peephole work can
remove the pair.

**`letrec*` semantics, for both `letrec` and `letrec*`.** Codegen for
`Letrec`:

1. push `Undefined` for every variable, and `MakeBox` the boxed ones;
2. evaluate each init in order and assign it;
3. compile the body, then `Slide` the variables away (unless in tail
   position).

R7RS allows `letrec` to be implemented this way. The two only differ for
programs R7RS calls errors.

**Use before initialisation is an error.** `BoxRef` checks for the
undefined value. That is the only check needed: a variable that can be
read before its init is, by rule 2, boxed. The error names the variable:
`variable used before its initialisation: b`. The name comes from the
instruction before the `BoxRef`, which is always the `LocalRef` or
`FreeRef` that loaded the box, and is looked up only on the error path.
The check itself is one comparison per `BoxRef`. s1 is laxer here: `(letrec ((a b) (b 1)) a)` gives
`#f` in s1.

**`set!` on an unbound global is an error** (`set!: unbound variable:
x`), as in s1.

**Internal definitions** are collected by the minimal expander:

- the leading `(define …)` forms of a `lambda`, `let` or `letrec` body
  become a `Letrec` around the remaining expressions;
- a `define` after an expression is an error, as is a body with no
  expressions, or the same name defined twice;
- `(define (f …) …)` names its procedure `f` here too.

The full R7RS body rules (definitions from a `begin`, from macro uses, and
`define-syntax`) come with P5's expander.

**Named `let`** is expanded to
`((letrec ((name (lambda (v …) body …))) name) init …)`, with the inits
outside the loop's scope. The loop variable refers to itself while
pending, so it is boxed, and each iteration does `FreeRef; BoxRef;
TailCall`. Calls to known local procedures are P10's item 4.

## Tests

`cargo test` runs 69 tests, all passing, and all also pass with
`S2_GC_STRESS=1 S2_GC_POISON=1`. New:

- **Assignment:** globals, an uncaptured parameter, `make-counter` with
  independent counters, two closures sharing a variable with the procedure
  that made them, a captured parameter boxed at entry.
- **`letrec` and internal definitions:** `even?`/`odd?` (to depth
  10,000), a recursive `letrec`, `letrec*` order, shadowing a global, and
  the errors above, including use before initialisation through a lambda.
- **Named `let`:** results, scope of the inits, and constant space.
- **Tail contexts:** five more from s1's `tail_tests.scm`: `letrec`,
  `letrec*`, named `let`, internal definitions, and a call after `set!`.
- **Golden:** `set` (box, slot and copy side by side) and `letrec`
  (`parity` and a named `let`).
- **Differential:** `tests/diff/p4-assignment.scm` gives the same output
  as s1.

One test was too slow at first: a million-iteration named `let` inside
`check`, which runs with GC stress on, made the unit tests take 48
seconds instead of about one. Ten thousand
iterations show constant space just as well.

## Measurements

The machine was busy throughout: a load average over 100, just after a
reboot (P4's first measurement attempt was abandoned at a load of 327).
Only the interleaved ratios are meaningful.

| | | | |
|---|---|---|---|
| `fib 30`, P3 vs P4 (medians of 9) | 0.17s | 0.17s | unchanged |
| `fib 30`, s1 vs s2 (`bench.sh 7`) | 0.61s | 0.17s | 3.6x |
| named-`let` loop, 3,000,000 iterations, s1 vs s2 (medians of 5) | 0.74s | 0.19s | 3.9x |

- `fib` compiles to the same code as in P3, and the extra instructions in
  the dispatch `match` cost nothing measurable.
- The named-`let` loop does a `BoxRef` per iteration, and is as fast
  relative to s1 as `fib`.

## Surprises

- The narrower rule for `letrec` boxing: working out exactly when a
  `letrec` variable can be copied too early showed that 03 §7's rule
  boxed more than it needed to.
- My first golden example for "assigned but not captured" captured the
  variable after all. The disassembly showed a `MakeBox` I hadn't
  expected, and the example was wrong, not the analysis.

## Correction (P7)

The boxing rule above is wrong once continuations can be re-entered. A
continuation copies the stack, so a `set!` variable in a plain stack slot
comes back with its old value when the continuation is re-entered. Since
P7, every `set!` variable is boxed, captured or not; see
[P7](P7.md#a-p4-design-error).
