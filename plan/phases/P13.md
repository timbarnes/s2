# P13. The compiler in Scheme

Planned in [08](../08-compiler-in-scheme.md), which settles the decisions
(C1-C11) and splits the phase into P13.0-P13.6. This file records each
sub-phase as it is done.

## P13.0. Groundwork

Done 2026-10-12. Nothing of the Scheme compiler yet: the interfaces it
will use, and the harness that will check it.

### What was built

| File | Change |
|---|---|
| (tag) | `rust-compiler`, on the commit before P13.0: the Rust-compiled engine as it was |
| `src/compile/data.rs` | new: the core AST as tagged vectors and back (C2); instructions as lists and back, from one table; `%make-template`, which builds a template from its fields and checks its operands (C1); `%template-instructions`, its inverse |
| `src/compile/mod.rs` | `generate`, the one entry point for code generation, and `S2_COMPILER`: `rust` (the default) or `roundtrip` |
| `src/main.rs`, `libraries.rs` | every code generation goes through `generate`. `--expand` and `--dis` now also print during `--compile` |
| `src/fasl.rs` | compiled files are reproducible |
| `tests/compiler.rs` | new: the oracle, and a reproducibility test |

### The oracle

`tests/compiler.rs` compiles a corpus with the Rust compiler and with
another `S2_COMPILER` choice, with `--expand --dis`, and requires the same
output line for line (C7). For now the other choice is `roundtrip`:

1. The Rust front end's AST becomes tagged vectors.
2. The vectors become an AST again.
3. The Rust codegen compiles it.
4. Every template is taken apart into `%make-template`'s arguments and
   made again, inner templates first.

This checks the converters that P13.1 needs, and the harness itself. A
deliberate change to one name in the round trip made the test fail, at the
right line of the right files.

**The corpus**, 58 files:

- **compiled only:** the golden files, `scheme/core.scm` and `bench/`;
- **run** (`-f`): the Scheme test files and chibi's suite, section by
  section.

Running gets past what compiling ahead can't do. `basic_tests` has a
circular constant, which compiled files can't hold. `library_tests`
writes a file and then includes it. Running also compiles what the
programs compile as they go (`eval`, `load`, library files), though only
the top-level forms are printed.

The whole test suite and chibi's suite also pass with
`S2_COMPILER=roundtrip`.

### Decisions

**The cargo feature waits for P13.5.** 08 had it in P13.0. Until P13.5
the Rust compiler is what builds the Scheme one, so a feature leaving it
out would have nothing it could leave out.

**Instruction names** are the `Op` names in kebab case (`local-ref`,
`jump-if-not-imm`), except the inlined predicates, which keep their
Scheme names (`null?`, `pair?`, `eq?`). A test in `JumpIfNot` is named
by its procedure (`<`, `null?`). One macro, listing each instruction once,
generates both directions, so the two can't disagree. A unit test round
trips every instruction.

### Bugs found

**Compiled files weren't reproducible**, as P11 noted. The cause: a
library environment's bindings were written in hash-table order, and the
table is keyed by addresses. Compiling the same file under GC stress gave
different bytes.

- **The fix:** sort the keys by name. Several hidden definitions can share
  a name: two `define-record-type`s in one library each make an `index`,
  keyed by different aliases. Those are ordered by where the code first
  uses what they are bound to.
- **The test** compiles a library with two record types, and `core.scm`,
  normally and under GC stress, and compares the bytes.

**A safety note, from P12.** The fixed value stack reads slots without
bounds checks in release builds. So a wrong slot index in a template,
from a damaged compiled file or a codegen bug, is now a memory error
rather than a panic. P11's note claiming otherwise is corrected.

`%make-template` checks everything it can without knowing the stack
depth: constant indexes, the kinds of constant instructions need, jump
targets and free-variable indexes. Slot indexes need a verifier that
tracks the depth through the code. 08's risks record it; until then, the
oracle and the debug-build test runs, where every access is checked,
stand in.

### Tests

`cargo test` runs 114 tests, all passing:

- release, debug and GC stress builds;
- the whole suite again with `S2_COMPILER=roundtrip`;
- chibi's suite at 1154 in both modes.

## P13.1. Codegen and analysis in Scheme

Done 2026-10-12. The back end of the compiler is Scheme, and with
`S2_COMPILER=scheme` it compiles the corpus to exactly the Rust
compiler's code.

### What was built

| File | Change |
|---|---|
| `scheme/compiler/ast.scm` | the AST's accessors (the only code that indexes its vectors); a growable buffer; list helpers R7RS-small lacks |
| `scheme/compiler/analyze.scm` | free variables, boxed variables, lambda groups, as `analyze.rs` |
| `scheme/compiler/codegen.scm` | code generation, as `codegen.rs`, instruction for instruction |
| `src/main.rs` | the files, wrapped as the library `(s2 compiler)`, load from a cached image (`s2-compiler.s2o`), as `core.scm` does, when `S2_COMPILER=scheme`. `Session::generate` calls its `codegen` |
| `src/vm/machine.rs` | `Vm::call`: Rust calling a Scheme procedure, at the top level |
| `src/compile/data.rs` | `%inline-instruction`: which instruction a call to a global is inlined as, shared with the Rust codegen (`codegen::inline_op`) |
| `tests/compiler.rs` | the oracle checks `scheme` as well as `roundtrip` |

About 570 lines of Scheme, comments included, replace about 690 of Rust (`codegen.rs` and
`analyze.rs`).

### How it went

**The oracle earned its keep.** The first run differed on every file
that used `caddr`, which is in `(scheme cxr)`, not imported. The
compiler's error was raised as a Scheme error with a backtrace, through
the same machinery as any program's. After that one fix, the whole corpus
matched. That includes the Scheme test files and chibi's suite run in
full.

A deliberate change, disabling `sub-imm`, failed the test at the right
line of four files. Editing a compiler file and rebuilding also rebuilt
the stale image, as P11's freshness rule intends.

**Two runtime tests depended on the size of the startup heap**, and
failed with the compiler loaded:

- `tail_calls_run_in_constant_space` required the stack never to exceed
  64 slots. The compiler now runs on that stack. It now checks that a
  million iterations go no deeper than ten.
- `deep_recursion_collects_in_linear_time` bounded the marking per
  collection. Every collection also re-marks the startup heap, which the
  compiler enlarges. That part is now subtracted, and the linear bound on
  the rest is unchanged.

**A harness bug.** The two oracle tests ran their Rust-compiler pass under
the same temporary file names, in parallel, so one deleted the other's
files. Each test now names its own files.

### Decisions

Recorded in 08:

- **Analysis came with codegen** (P13.2 is folded in). Reaching the Rust
  analysis from Scheme would have needed primitives written to be
  discarded a sub-phase later.
- **The compiler is the library `(s2 compiler)`**, not `%` names in the
  system environment (C10 changed). Loading it from a compiled image
  needs no compiler, so the library machinery is no obstacle. Its names
  stay private.
- **Where the Scheme codegen runs.** It runs where the VM can call it: the
  REPL, `-e`, `-f`, programs and `--compile`. Library files and `eval`
  compile inside a primitive, so they keep the Rust codegen until P13.4.

### Measurements

Release build, wall time per run, the median of 20. Expansion is still
Rust, so the difference is the Scheme back end, plus converting each
form's AST to vectors and calling into the VM.

| | Rust | `S2_COMPILER=scheme` |
|---|---|---|
| Startup (`-e 1`) | 3.0ms | 3.5ms: the compiler's 30KB image |
| `--compile scheme/core.scm` (516 lines) | 4.0ms | 7.5ms |
| `--compile` four test files (1,034 lines) | 6.0ms | 18.5ms |

Less startup, compiling is 3.5-5 times slower: still a few milliseconds
per thousand lines. Nothing has been tuned. The likely costs are the
association lists for variable locations and names, and the linear
search of the constant pool.

### Tests

`cargo test` runs 115 tests, all passing:

- with the Rust compiler and with `S2_COMPILER=scheme`;
- release, debug, and GC stress with poisoning;
- chibi's suite at 1154 with either compiler.

## P13.3. The front end in Scheme

Done 2026-10-12. With `S2_COMPILER=scheme`, the whole compiler is
Scheme: `syntax-rules`, the expander and library declarations, then
P13.1's codegen. Over the corpus it gives exactly the Rust compiler's
`--expand` and `--dis` output.

### What was built

| File | Change |
|---|---|
| `scheme/compiler/syntax-rules.scm` | parsing `syntax-rules` (with the Rust messages), matching (ellipses, literals, vectors, improper patterns) and instantiation, as `syntax_rules.rs` |
| `scheme/compiler/expand.scm` | the expander, as `expand.rs`: every core form, bodies in two passes, quasiquote, `let-syntax`, and the Rust expander's variable numbering |
| `scheme/compiler/libraries.scm` | library names, import sets, `define-library` declarations, `include`, `cond-expand` |
| `src/compile/prims.rs` | 20 primitives over what stays Rust (C3): aliases, environments and their cells, macros as data, the library registry, reading included files |
| `src/main.rs` | `Session::compile`: Scheme `expand` then `codegen`, or the Rust pair. `--expand` prints the Scheme AST through P13.0's converter |
| `scheme/compiler/codegen.scm` | `expr` renamed `gen-expr`: the library is one scope, and the expander has its own `expr` |

About 1,080 lines of Scheme, comments included, replace about 1,520 of
Rust (`expand.rs` and `syntax_rules.rs`). The library code in
`libraries.rs` stays, for the Rust front end, until P13.6.

### How it went

**It matched the oracle on the first run that built.** Getting it to
build took three fixes:

- **Two stray parentheses** closed the library's `begin` early. The
  error was "unknown declaration", far from either one. A paren counter
  found them.
- **Name clashes in one library.** The record type `transformer` shadowed
  the expander's procedure of that name. `expr` was defined in both
  `codegen.scm` and `expand.scm`: the later one won, codegen produced
  empty templates, and the VM panicked indexing them. R7RS makes a
  duplicate definition in a library body an error, and s2 doesn't report
  it. It should.
- **A two-list `map-in-order`** in `letrec`, which takes one list.

A deliberate change, expanding `if`'s branches in the other order,
changed the variable numbering. The oracle failed on `core.scm` and the
derived-form tests.

**One test took hours.** Every unit test collects at every safepoint.
With the Scheme front end each collection also marks the compiler's
image, and `deep_expansions` expands a 1,000-argument `or` and a macro
that recurses 10,000 deep. Both now run unstressed. They test the
expander's depth, which stress doesn't change.

### Decisions

Recorded in 08:

- **Macros stay Rust `SyntaxRules` objects** (C4 changed). The Scheme
  expander reads and makes them through `%macro-parts` and
  `%make-macro`. The two front ends share macros, in environments and in
  compiled files, and the fasl format is unchanged.
- **`pending_load` stays until P13.4.** Library files and `eval` still
  compile inside a primitive, with the Rust front end. The Scheme front
  end loads a library with a direct call to `%load-library`.
- **No separate matcher test.** The oracle covers every macro use in the
  corpus.

### Measurements

Release build, wall time per run, the fastest of 20.

| | Rust | `S2_COMPILER=scheme` |
|---|---|---|
| Startup (`-e 1`) | 3.2ms | 3.6ms |
| `--compile scheme/core.scm` (516 lines) | 4.1ms | 11.3ms |
| `--compile` the compiler's own source (1,655 lines) | 7.5ms | 59.2ms |

Less startup, the Scheme compiler is 8-13 times slower: about 33ms per
thousand lines, against 3ms. Both produce identical files. Nothing has
been tuned. Expansion is the new cost: environments are association
lists, and each macro use goes through `%macro-parts`, which copies its
rules.

### Tests

`cargo test` runs 115 tests, all passing:

- with the Rust compiler and with `S2_COMPILER=scheme`;
- release, debug, and GC stress with poisoning;
- chibi's suite at 1154 with either compiler.

## P13.4. The driver

Done 2026-10-12. With `S2_COMPILER=scheme`, every compile goes through
the compiler in Scheme: the REPL, `-e`, `-f`, programs, `--compile`,
`load`, `eval`, imports and library files. Only the bootstrap, which
compiles `core.scm` and the compiler itself into their images, uses the
Rust compiler.

### What was built

| File | Change |
|---|---|
| `scheme/compiler/driver.scm` | `compile`; `eval-form`, which is `eval`; `load-library`, which loads a library file from its compiled file or compiles it, form by form, and writes the compiled file |
| `src/main.rs` | the compiler exports `eval-form` and `load-library`, and s2 binds the system's `eval` and `%load-library` cells to them. After an error, `abandon_compiles` |
| `src/libraries.rs` | `%cached-library`; `%library-compile-begin` and `-end`, which record a library file's changes and sources, as `compiled_library` does, but on a stack, since compiles now nest |
| `src/compile/data.rs` | `%template->procedure` |

45 lines of Scheme. The Rust they replace stays, for the Rust front end.

### How it went

**Two cells did it.** `load`, imports, library files and Rust's own
`load_library` all call `eval` or `%load-library` through the system
environment's cells. Binding those two cells to the Scheme versions
moved every compile to Scheme, with no caller changed. To check this,
a temporary trace printed every use of the Rust expander. In Scheme
mode it printed nothing over the tests and chibi's suite, apart from
the 66 forms of the bootstrap.

**Loads nest now.** The Rust path couldn't load a library in the middle
of compiling one. It failed, set `pending_load`, and its caller loaded
the library and started again. The Scheme compiler just loads it. So
the recording of what a library file changes (`touched`) and which
files it reads (`reading`) moved from a Rust function's locals to a
stack, popped by `dynamic-wind` when a compile ends, and by
`abandon_compiles` when an error ends the top-level form.

**One bug before the tests ran:** `interaction-environment` is in
`(scheme repl)`, which the compiler library didn't import.

**Compiled library files are identical.** The `.s2o` the Scheme
compiler writes for a library is byte for byte the Rust compiler's.

**A backtrace difference.** A compile error inside `eval` shows
`in compile` and `in eval-form` where the Rust path showed `eval`'s
caller. The caller made a tail call to `eval-form`, so its frame is
gone. The messages are the same. Left as it is.

### Decisions

Recorded in 08:

- **The switch is two cells**, not a change to each caller, while both
  front ends are selectable.
- **`pending_load` and `%load-then-eval` stay, unused in Scheme mode.**
  The Rust front end needs them, and the fasl reader uses `pending_load`
  when a compiled file needs a library loaded first. They go with the
  Rust compiler, behind P13.5's cargo feature.
- **A library file compiles one form at a time**, each run before the
  next is compiled. The Rust path compiles the whole file and, if that
  fails, evaluates it form by form instead. For a file of several
  libraries that import each other, only the second way works.

### Measurements

chibi's suite, 20 sections in a process each, wall time: 0.74-0.78s
with the Rust compiler, 0.89-1.21s with the compiler in Scheme. That is
10-20ms more per section, mostly compiling.

### Tests

`cargo test` runs 115 tests, all passing:

- with the Rust compiler and with `S2_COMPILER=scheme`;
- release, debug, and GC stress with poisoning.

chibi's suite is at 1154 with either compiler. In Scheme mode under GC
stress, it is also at 1154, given a longer per-section timeout
(`S2_TIMEOUT=900`). With the default 15 seconds, 166 tests time out.

## P13.5. Self-compilation

Done 2026-10-12. The compiler in Scheme compiles itself to a fixed
point, and s2 builds and passes its tests without the Rust compiler.

### What was built

| File | Change |
|---|---|
| `src/main.rs` | `--core-image OUT` and `--compiler-image OUT`: the images s2 starts from, compiled by the compiler selected. `S2_CORE_IMAGE` and `S2_COMPILER_IMAGE` name images to start from. `build_image`, shared with the startup cache |
| `Cargo.toml` | the feature `rust-compiler`, on by default |
| `src/compile/`, `src/libraries.rs`, `src/vm/` | gated by the feature: the expander, the matcher, analysis, codegen, the Rust half of the library code, `pending_load`, the VM's `eval` |
| `src/fasl.rs` | `fasl::read` returns `Loaded::Needs(file)` when a library must be loaded first, instead of setting `pending_load` |
| `src/globals.rs`, `src/compile/data.rs` | the core-form table, and `inline_op`, moved out of the gated files: the rest of s2 uses them |
| `scheme/compiler/driver.scm` | `dis-form`, which `dis` is bound to |
| `tests/compiler.rs` | the fixed-point test |
| `tests/no-rust.sh` | the exit test: build without the Rust compiler, from stage-2 images, and run everything |

### How it went

**The fixed point held at once.** Stage 1, the compiler image
compiled by the Rust compiler, stage 2, compiled by stage 1, and
stage 3, compiled by stage 2, are the same 61,074 bytes. So is
`core.scm`'s image, compiled by either compiler. Identical code (C7)
predicted this.

**`core.scm`'s image needed its own environment.** The running system
environment already has core's bindings, so compiling core into it
again would record nothing new. `--core-image` compiles it for a fresh
environment, built as the system environment is at startup, and that
environment stands in as the system environment while it compiles:
`global-call` takes its cells from there. The real one is pinned
meanwhile. Under GC stress the image is still the same bytes.

**The Rust compiler was less tangled than expected.** Seven errors when
first built without it. Two kinds of thing it held are shared: the table
of core forms, which environments and compiled files use, and
`inline_op`, which the Scheme codegen asks. Both moved out. The rest is
gated whole (`expand`, `codegen`, `analyze`) or item by item (the
matcher in `syntax_rules.rs`, the Rust import resolution in
`libraries.rs`).

**`dis` still used the Rust compiler** in Scheme mode, found when the
gated build failed to compile it. It now goes through `dis-form`.

**The two builds made different images at first.** Without the Rust
compiler, `%compiled-library` wasn't bound, so `core.scm`'s reference to
it made a new cell, and the image had one binding more. It is now bound
in both builds, and an error without the Rust compiler. The build
without it rebuilds its own images to the same bytes.

### Decisions

Recorded in 08:

- **Images for the build without the Rust compiler come from a default
  build** (C5's option a, kept). Committed boot images remain P13.6's
  decision.
- **`pending_load` is gated, not deleted**, until the Rust compiler goes.
  The fasl reader no longer needs it.
- **Each image is used however old it is**, in that build: nothing there
  can rebuild it at startup. `--core-image` and `--compiler-image` still
  can.

### Measurements

The release executable, stripped: 1.59MB with the Rust compiler,
1.46MB without, 8% less. The gated Rust is about 2,200 lines: the
expander, analysis and codegen (1,468) and most of the matcher and the
library code.

### Tests

- Default build: 116 tests, all passing, with the Rust compiler and with
  `S2_COMPILER=scheme`; release, debug, and GC stress with poisoning.
  chibi's suite at 1154 with either.
- Without the Rust compiler (`tests/no-rust.sh`): 106 tests, all
  passing, also under GC stress, and chibi's suite at 1154. The other 10
  need the Rust compiler: the oracle, the fixed point, the Rust matcher's
  own tests and the Rust `--expand` test.
