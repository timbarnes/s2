# P11. Bytecode files

Done 2026-10-11. s2 compiles a program to a file and runs it without
compiling again. Library files are cached compiled, next to their `.sld`,
and recompiled when they change. `scheme/core.scm` loads from a compiled
image, so starting s2 no longer compiles it: startup went from 3.5ms to
2.95ms.

```
s2 --compile prog.scm            # writes prog.s2o; runs nothing
s2 --compile prog.scm -o out.s2o
s2 prog.s2o ARG ...              # as s2 prog.scm ARG ...
```

## What compiled code depends on

This was the phase's real question. A template's code and names are plain
data. Its constants are where it reaches the rest of the system:

- **Literals** (numbers, strings, symbols, lists, vectors): written as data.
  Symbols are interned again on load, so `eq?` still holds between them.
- **Inner templates**: written like any other object.
- **Binding cells** (D7): the compiler puts the cell itself in the pool, so
  a global reference is one load. A new process has its own cells, so a
  cell is written as *which environment, and which identifier*, and found
  again on load. If the environment is the one the file loads into, or one
  the file creates (a `define-library`'s), the cell is found or made. In
  the system environment or a library from elsewhere, it must exist
  already. The writer learns which environment a cell belongs to by
  looking it up in every candidate environment, since a cell doesn't
  record that itself.

**Compiling also changes environments.** Expanding a file runs `import`,
`define-syntax` and `define` as each form is expanded (P5, P8), before
anything runs. Compiled code doesn't need those bindings, since its cells
are resolved directly, but later code does: the REPL after `load`,
`eval`, and the standard libraries, which export `core.scm`'s macros. So
every binding change now goes through one method, `Env::bind`, which
records the identifier while a file is compiled (`touched`). The compiled
file holds the final binding of each recorded identifier, and loading
makes them again *before* the file's code runs. That is one difference
from loading the source: there, a binding appears when its form is
reached. Code that inspects an environment while the file loads can tell.

**Macros** are written as their parsed rules: the literals, the
(pattern, template) pairs, and the definition scope. The roadmap expected
to store `syntax-rules` source and parse it again on load. That isn't
needed: P5's parsed form is already plain data. A macro defined elsewhere
(`cond`, imported by a library) is written as (environment, name), like a
cell, so loading finds the system's `cond` rather than making a copy. That
halved the size of a library's cache file.

**Aliases**, the identifiers macro expansions rename (P5), are written as
objects, so they keep their identity within a file. This matters for
hidden definitions: `define-record-type`'s field index (P10) is defined
under an alias, and the accessors refer to the same alias. After loading,
both find the same cell.

**Cycles.** Environments contain macros, and macros refer to the
environment they were defined in. The object table refers only backwards,
so the reader is one pass. Environments are written empty, and their
bindings in a section after all the objects. Circular constants (datum
labels, `'#0=(a . #0#)`) are refused when compiling.

## Decisions

**D5's second half: the byte encoding.** Each instruction is a tag byte
followed by its operands as LEB128 varints. The loader decodes it into
`Op`s, and the VM is unchanged. The roadmap asked for a measurement of
running from bytes instead. I didn't build one: it means a second
dispatch loop that decodes operands on every instruction. Decoding happens
once per load, and a whole 27KB file loads in 0.26ms. The case for running
from bytes is memory, and nothing here is short of it.

**What compiling runs.** Nothing of the file, except:

- **libraries it imports** are loaded, as for any import, so their exports
  can be compiled against;
- **`define-library` forms in the program itself** are run when compiled,
  so the forms after them can import them, as chibi's suite does with its
  test library. When the file is loaded, the library's code runs again and
  registers it there. The writer tells such a library from one loaded from
  elsewhere because its environment is among the file's own constants.

One consequence: a macro whose literal is a global variable compares it as
unbound while compiling (P8's literal matching checks whether a global is
bound), where a source run would have defined it by then. No test is
affected.

**Library files are cached next to their source**, as `foo/bar.s2o`
beside `foo/bar.sld` (roadmap). The cache is used if it is *fresh*:

- every file read while compiling it (the `.sld` and anything it
  `include`s) still has the modification time it had;
- the running `s2` was built before the cache was written. A rebuilt s2 may
  compile differently, so it compiles again.

Caching is best effort:

- a cache that can't be written, or read, is ignored;
- one is written whole, then renamed into place, so parallel test runs
  never read half a file;
- a library file that can't be compiled ahead (one whose second
  `define-library` imports its first) is evaluated form by form as before,
  which also reports its errors as before.

`*.s2o` is in `.gitignore`.

**The format has a version number** (`fasl::VERSION`), bumped by hand when
the encoding or the meaning of an instruction changes. A file of another
version is refused with a message. Caches are also invalidated by the
build-time check above, so the version matters most for compiled programs
kept across s2 versions.

**`core.scm` loads from an image cached next to the executable**
(`s2-core.s2o`), under the same freshness rule, and is written the first
time s2 runs after a build. 06 said the image would be "shipped". A cache
is simpler for now:

- it can never be stale;
- it puts no binary in git.

P13 will need an image in the repository: a compiler written in Scheme
can't compile itself without one. That is P13's decision. If the image
can't be written (s2 installed somewhere read-only), s2 compiles
`core.scm` at every start, as before.

**Not done:**

- **A separate `s2c` binary.** `--compile` is enough.
- **Validating instruction operands on load.** The loader checks the file's
  structure: every truncation of a file is an error, tested byte by byte.
  It doesn't check that a constant index or jump target is in range, so a
  damaged file of the right shape can make the VM panic. That is a crash,
  not memory corruption: the VM has no unchecked indexing. *(No longer
  true after P12: the fixed value stack reads slots unchecked in release
  builds. See P13.0.)*
- **Reproducible output.** The bindings section follows hash-table order,
  so compiling twice can give different bytes. *(Fixed in P13.0.)*

## Measurements

Release build.

| | before | after |
|---|---|---|
| Loading `core.scm` at startup | 0.7-1.0ms compiled | 0.2ms from a 17KB image |
| `s2 -e 1`, per run (P10's build against P11's, 200 runs each, alternating, four rounds) | 3.5-3.6ms | 2.95ms |
| A 13KB program (a section of chibi's suite): compile, or load | 2.0ms to compile and write | 0.26ms to load the 27KB file |

The benchmarks are unchanged against P10 (`bench.sh --compare`, all
within 1.00-1.04x): nothing in the VM changed.

The compiled file is about twice the size of its source. A library's cache
is about 5KB, most of it the names of the 240 or so bindings it imports
from `(scheme base)`.

**Chibi's suite, compiled.** Each of the suite's sections, prepared as
`run.sh` prepares it, was compiled and run, and its output compared with
the source run:

- 18 of the 20 sections give identical output;
- 1 can't be compiled: it contains complex-number literals, which the
  reader rejects;
- 1 stops early, at a top-level error from reading `1+2i` at run time.
  `-f` reports such an error and carries on; a program, compiled or not,
  stops.

For short programs, compiling ahead saves little: s2 compiles a 13KB file
in 2ms, less than its 3ms startup. Its real uses are startup (the core
image), libraries loaded by many programs, and the boot image P13 needs.

## Bugs found

**Nested recording.** Compiling a program that imports a library file
compiles the library, and that inner compile replaced the program's list
of changed bindings, then cleared it. The program's own `import` and
`define-syntax` were lost from its compiled file. Found by the first test
of a compiled program. Both the library compile and `fasl::read`, which
also binds, now set the caller's list aside and restore it.

## Tests

`cargo test` runs 106 tests, all passing, with and without the core image
and library caches present, and all also pass with
`S2_GC_STRESS=1 S2_GC_POISON=1`.

New tests:

- **A compiled program** (unit test, loaded under GC stress):
  - every kind of constant;
  - an import of a library file;
  - a record type, whose hidden definitions are keyed by aliases;
  - a macro, used by code compiled after the file is loaded;
  - `car` before and after the file defines its own;
  - a named-let loop;
  - an assigned global.

  Also, a circular constant is refused.
- **Damaged files**: every truncation of a compiled file is an error, and
  another version is refused.
- **A compiled program, run as a process**: same output, arguments and
  exit status (70 after an error) as its source.
- **A library cache**: written on first use, used unchanged on the
  second, and recompiled once the library's source changes.

The rest of the suite exercises the library cache, since every library
file now loads through it: the first run of `cargo test` compiles them,
and later runs load the caches.
