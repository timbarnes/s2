# P2. `lambda`, local variables, closures and tail calls

Done 2026-10-10. `fib` runs 3.3-4x faster than s1. A million-iteration
tail-recursive loop runs in constant space.

```
s2> (dis '(define (fib n) (if (< n 2) n (+ (fib (- n 1)) (fib (- n 2))))))
template top-level
   0  MakeClosure k0   ; #<template fib>
   1  GlobalDefine k1  ; fib
   2  Return
template fib  arity 1
   0  GlobalRef k0     ; <
   1  LocalRef 0       ; n
   2  Fixnum 2
   3  Call 2
   4  JumpIfFalse →7
   5  LocalRef 0       ; n
   6  Return
   7  GlobalRef k1     ; +
   8  GlobalRef k2     ; fib
  ...
  19  Call 1
  20  TailCall 2
```

This is instruction for instruction the listing predicted in 03 §6.

## Decisions

**D6: flat closures, with no boxes yet.**

- A closure is `Obj::Closure { template, free: Box<[Value]> }`. When it is
  made, it copies the *values* of its free variables. Inside the body they
  are `FreeRef i`.
- Codegen pushes each free variable's value, using `LocalRef` or `FreeRef`
  depending on where that variable lives in the *enclosing* procedure.
  `MakeClosure k` then pops them into the new closure.
- A variable free two levels down is captured by the middle lambda too, so
  the inner one can copy it from there (see `tests/golden/closures.dis`,
  `adder3`).
- This is only correct because nothing can be assigned yet. Copying the
  value of a variable that is later `set!` would give the closure a stale
  copy. P4 adds `set!`, and with it boxes for variables that are both
  captured and assigned.

**Free-variable analysis is one small function** (`analyze.rs`). Because
the expander gives every binding a unique `VarId`, it needs no scope
tracking. A variable is free in a lambda if it is referenced anywhere
inside the lambda and bound nowhere inside it. The function is recomputed
for each nested lambda: O(size × depth), marked `ponytail:`.

**Tail positions are decided in codegen, not in a separate pass.** The walk
carries a `tail` flag, which is true for a lambda body and for a whole
top-level form:

- `if` passes the flag to both branches;
- `begin` and `let` pass it to their last expression;
- a call in tail position becomes `TailCall`;
- any other expression in tail position is followed by `Return`.

A tail `if` therefore needs no `Jump` over its else-branch, because the
then-branch has already returned. Compare the old and new `if.dis`.

A separate tail analysis would duplicate exactly this recursion, so 03 §1's
"tail positions" analysis lives here instead.

**The top-level form is a procedure too.** `Vm::run` wraps the template
in a closure with no free variables and runs it with `fp = 1`, exactly as
if it had been called. So a call that ends a top-level form is a
`TailCall`, and the golden files changed from `Call; Return` to
`TailCall`.

**Frame layout and calling convention** (03 §5, §9):

```
value stack:  … │ callee │ arg0 … argN-1 │ let variables │ temporaries │
                           ▲ fp
frame stack:  Frame { closure, ip, fp }
```

- `LocalRef i` is `stack[fp + i]`.
- The running closure, template and free variables are held in local
  variables of the dispatch loop (registers), not re-read from the frame.
- `Call n` on a closure checks the arity and collects a rest list. It then
  pushes the caller's `{closure, ip, fp}` and sets `fp = base + 1`.
- `Return` truncates to `fp - 1` (removing the callee and everything above
  it), pops the frame, and pushes the result.
- The frame stack is separate from the value stack, as planned. This keeps
  `Value` free of return-address types, and lets `%frame-depth` count
  frames directly.

**How `TailCall` moves arguments.**

- `stack.drain(fp - 1 .. base)` slides the new callee and its arguments
  down over the current procedure's slots, which also discards its locals
  and temporaries.
- The callee is then entered with the *same* `fp` and no new frame.
- A tail call to a primitive calls it, then does the `Return` sequence
  with the result.
- `Vec::drain` is a `memmove` of `argc + 1` values: simple, and cheap for
  realistic argument counts.

**`let` variables are stack slots, and codegen tracks the stack depth.**

- Codegen knows how many values each instruction pushes and pops, so it
  always knows `depth`, the number of values in the current frame.
- A `let` variable is simply the slot its init's value landed in: its slot
  number is the depth when that init began.
- In tail position nothing more is needed, because the frame goes away. In
  any other position, `Slide n` keeps the body's value and drops the `n`
  variables beneath it.
- A `let` therefore costs no closure and no frame (03 §2's reason for
  keeping `Let` in the AST).
- Sibling `let`s reuse the same slots. The disassembler shows a reused
  slot's names joined with `/`.

**Arity is checked at entry**, from `Template.required` and `rest`, as 03 §9
planned. The error names the procedure and what it expected:
`f: wrong number of arguments: 2 (expected 1)`, or `(expected at least 1)`
for a procedure with a rest parameter. A rest list is built from the
surplus arguments on the stack.

**Templates and closures are heap objects.** A template's constant pool
holds the templates of its inner lambdas, so templates must be `Value`s.
P3's collector traces through them like any other object.

**Procedure names.** `(define (f …) …)` and `(define f (lambda …))` name
the lambda `f`, which is used in printing (`#<procedure f>`, as in s1),
in arity errors and in the disassembler. Anonymous procedures print as
`#<procedure>`, again as in s1.

**The expander now has lexical scope.**

- It keeps a stack of `(symbol, VarId)` pairs, and a symbol bound there is
  a `LocalRef`.
- A local variable named like a keyword shadows it: `((lambda (if) (if 1
  2)) cons)` is `(1 . 2)`.
- Not yet supported: internal `define`, which comes with `letrec*` in P4,
  and named `let`, which needs `letrec`. Both give clear errors.

**VM primitives get the `Vm`.** `%frame-depth` needs to see the frame
stack, so `VmFn` now takes `&mut Vm` as well. The arguments are copied out
of the stack for these calls, since the stack belongs to the `Vm` being
passed. There are few such primitives and they are cold, so the copy
doesn't matter.

**`%frame-depth`** returns the number of frames waiting for a return. It is
s2's version of s1's `%kont-depth`, used by the same tail-call tests.

**mimalloc** is now the global allocator, as in s1, so the benchmarks
compare like with like (P0 deferred this to here).

## Tests

`cargo test` runs 63 tests, all passing:

- **Result tests:**
  - procedures, names and printing;
  - rest arguments in every form;
  - closures: currying, `compose`, a capture two levels deep, independent
    copies per closure;
  - `let` scoping: inits outside the scope, shadowing of globals and
    keywords, sibling slot reuse;
  - arity and syntax errors;
  - an error deep in a call chain, after which the VM still works.
- **Constant space:** `(loop 1000000)` returns frame depth 0. Afterwards
  the value and frame stacks' capacities, which only ever grow, are both
  under 64.
- **Tail contexts** (from s1's `tail_tests.scm`): `(loop 5)` and
  `(loop 500)` reach their base case at the same frame depth in each tail
  context P2 has: both `if` branches, `let` body, `begin`, and lambda body,
  with single and multiple body forms. A control check confirms that a
  non-tail call does grow. The other 24 contexts in s1's file need later
  forms (`cond`, `and`, named `let`, `apply`, `call/cc`, …). They will be
  ported as the forms arrive.
- **Golden:** new `fib`, `closures`, `let`, `tail` and `rest` cases. The
  old ones changed only where a final `Call; Return` became `TailCall`.
- **Differential:** `tests/diff/p2-procedures.scm` gives the same output on
  s1 and s2.

## Measurements

`bench/bench.sh 9` (medians of 9 runs, s1 and s2 interleaved), on an Apple
silicon laptop:

| | s1 | s2 | s1 / s2 |
|---|---|---|---|
| `fib 25` | 0.20s | 0.06s | 3.3x |
| `fib 30` | 2.10-2.78s | 0.59-0.70s | 3.6-4.0x |

- **Absolute times drift a lot between runs** on this machine: s1 alone
  ranged from 1.3s to 2.8s on `fib 30` across sessions. The first version
  of `bench.sh` ran all of s1's repetitions, then all of s2's, and its
  ratios were unreliable. It now interleaves the two systems, as s1's own
  benchmarking practice does, and prints the ratio. Only the ratios should
  be compared across sessions.
- **Startup is negligible** for both (under 10ms), so `fib 25` isn't
  dominated by process start.
- `fib` allocates nothing in s2: fixnums are unboxed, and calls push onto
  existing vectors. Maximum resident memory for `fib 30` was 2.8MB. In s1
  every integer is a heap `BigInt`.

**Where s2's time goes** (by inspection, not yet profiled): each `fib` call
makes three primitive calls (`<`, `-`, `+`), each going through the full
`Call` path. That means a type dispatch, an arity check, an indirect call,
and a fixnum check on every argument. That is exactly what P10's inlined
primitives remove. The README target is 5-10x, and P2 reaches 3.3-4x with
none of the planned optimisations, which is on track.

**One fix made during measurement.** The comparison builtins (`<`, `=`,
`>`) collected their arguments into a `Vec` on every call. They now walk
the arguments in pairs without allocating. I didn't get a clean
interleaved before/after for this change (it was made before `bench.sh`
was fixed), so its effect isn't recorded separately.

## Surprises

- The noisy machine; see above.
- Making the top-level form an ordinary procedure called with `fp = 1`
  removed a special case from the VM, and made top-level calls tail calls
  for free.
- `TailCall` to a primitive needs the full return sequence, because the
  current frame must go away. A `macro_rules!` inside the dispatch loop
  (`do_return!`) shares the sequence between `Return` and that case
  without a function call, since it updates the loop's registers.
