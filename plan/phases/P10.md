# P10. Performance

Done 2026-10-11. Five optimisations were measured and kept, and three of
the roadmap's items were measured and set aside. s2 is now 6.2x faster
than s1 on `fib` and 5.9x on the typical program, inside the README's
5-10x target.

Against s1 (`bench/bench.sh 7`, medians), before P10 and after:

| workload | before | after |
|---|---|---|
| deeprec | | 7.67x |
| fib | 3.94x | 6.23x |
| gen | | 2.73x |
| guard | | 4.60x |
| listmap | | 5.72x |
| macro-loop | | 13.52x |
| program | 4.70x | 5.87x |
| tail | | 5.26x |
| tak | | 7.42x |

Only `fib` and `program` were measured against s1 before P10; the other
workloads were written during it.

## Method

As planned (plan/05 §7):

- **Workloads.** `bench/` now holds nine of them: s1's `fib`, typical
  program and macro loop; tail calls, deep recursion and `map`; the
  generator and `guard` loop planned for s2; and `tak`. They are sized to
  run 0.2-0.6s on s2, since `/usr/bin/time` has 10ms resolution.
- **Comparisons.** `bench/bench.sh` runs s1 against s2, and
  `bench/bench.sh --compare OLD NEW` runs two s2 builds. Either way, runs
  of the two binaries alternate and the table shows medians (of 9, for
  the item comparisons). Builds before a change come from a `git
  worktree` of the last commit.
- **Instruction statistics.** `--features stats` counts executed
  instructions by opcode and by consecutive pair (`vm/stats.rs`), and
  prints them at exit. It is compiled out of normal builds.
- **Profiles.** `sample`, on longer runs of the same programs.
- **Noise.** Differences of up to ±5% between identical code (the
  workloads an item doesn't touch) are noise. Where an item's expected
  gain was near that, it was timed again on a 5x longer run.

## Kept

Each line compares the build before the item with the build after it.

**1. Inlined primitives** (03 §11). A call to `car`, `cdr`, `cons`,
`null?`, `pair?`, `eq?`, `not`, or two-argument `+`, `-`, `=`, `<`, `>`,
`<=`, `>=` compiles to one instruction, when the callee is the *system
environment's* binding of that procedure. The instruction handles a pair
or two fixnums itself, and calls the builtin's own function otherwise, so
results and errors are the builtin's. `fib`'s body went from 21
instructions with five calls to 18 with two.

| deeprec | fib | gen | guard | listmap | macro-loop | program | tail | tak |
|---|---|---|---|---|---|---|---|---|
| 1.50x | 1.50x | 1.00x | 1.17x | 1.20x | 1.17x | 1.12x | 1.62x | 1.57x |

This decides D9's REPL question, and the answer came free from P8. Inlining
is only correct if the binding can't change. Since P8, the system
environment's cells can't: user code can't `set!` an imported name, and a
`define` of one makes a new cell in the interaction environment. Code
compiled before such a `define` keeps the system's binding, inlined or
not. So the REPL gets inlining with no change in meaning.

**2. `letrec` of lambdas without boxes** (*Fixing Letrec*). A *lambda
group* is a `letrec` whose inits are all lambdas, none of whose variables
is assigned. A named `let` is one, as are internal procedure definitions.

- No init runs any code, so nothing can use a member before its init.
- The members need no boxes. The closures are made in order, capturing
  the slot's placeholder for any member made later, and then
  `PatchFree c i v` fills each placeholder in.
- Closure slots became `Cell`s for this; reading one costs the same.
- A named `let`'s loop no longer does `FreeRef; BoxRef` per iteration.

| listmap | macro-loop | others |
|---|---|---|
| 1.15x | 1.11x | 0.94-1.00x (noise; their code didn't change) |

`map`'s own loop in `core.scm` is a named `let`, hence `listmap`.

**3. A superinstruction**, chosen from the pair counts. An `if` whose test
is an inlined comparison or predicate compiles to `JumpIfNot(test, t)`
instead of the test, then `JumpIfFalse`. In `fib`, `Lt JumpIfFalse` was 9%
of all instructions.

| macro-loop | fib | tail | others |
|---|---|---|---|
| 1.20x | 1.04x | 1.04x | noise |

Smaller than the counts suggested. Removing 9% of `fib`'s dispatches
gained 4%, so dispatch itself isn't the bottleneck: calls and returns are.

**Frames cache their template.** A frame now saves the caller's template
and free variables as well as its closure, so `Return` doesn't look them
up again through two type checks. Argument binding has an inline fast
path for the usual case, the right count and no rest list.

| listmap | macro-loop | deeprec | others |
|---|---|---|---|
| 1.11x | 1.11x | 1.06x | 1.00-1.04x |

**4. Calls to known local procedures**, the simplest kind: self tail
calls. Inside a lambda-group procedure (a named `let`'s loop), its own
name always means the running closure, since the group's variables are
never assigned. So a tail call to it with the right argument count is
`SelfTailCall n`: move the arguments into the parameter slots and jump to
the start, with no closure check, no template lookup and no binding. It
still reaches a GC safepoint, as every loop must.

| macro-loop | others |
|---|---|
| 1.16x | 1.00x |

**Record accessors by index.** Each accessor looked its field up by name
on every call: P6's `ponytail:` note, and about 5% of the typical
program's profile. `define-record-type` now finds the index once, in a
definition only its expansion can see (P5's hidden definitions), and the
accessor reads by index. The typical program, on a 5x run: 1.20s to
1.17s, 2.5%.

## Set aside, with the measurement

**5. Multiple values on the stack.** No workload makes many. In the
`guard` loop, each iteration runs about 110 instructions and makes 8
closures and 15 calls in the Scheme-level exception code; making and
spreading values is a small part of that.

**6. The tagged-word `Value`.** The one item left that would speed up
everything (8-byte values instead of 16), and by far the largest change:
`value.rs` was designed so it could be done there alone, but flonums would
need boxing, which costs float-heavy code. The profiles can't separate
memory traffic from the rest of the dispatch loop, and the targets are
met. It stays a candidate if speed is wanted later.

**7. A segmented stack.** Copying the stacks for `call/cc` (D8) is about
13% of the generator benchmark, the workload it should matter most for
(`memmove` and the copies' allocation, in a profile). The generator's
weak ratio against s1 (2.7x) is mostly the Scheme-level `call/cc` wrapper
and allocation, not the copying. P7 already found deep captures 4.2x faster
than s1's O(1) capture.

**8. Constant folding.** None of the workloads compute with constants
that folding would remove.

## What else changed

- `bench/bench.sh` covers every workload, and has `--compare`.
- `--features stats` and `vm/stats.rs` (plan/05 §7).
- The golden listings changed with items 1-4 (reviewed: the inlined
  instructions, `JumpIfNot`, `PatchFree` and `SelfTailCall` in place of
  calls, boxes and jumps).
- `Heap::closure` takes an iterator, so `MakeClosure` drains the stack
  straight into the closure.

## Tests

`cargo test` runs 102 tests, all passing, and all also pass with
`S2_GC_STRESS=1 S2_GC_POISON=1`. chibi's suite stays at 1,154. Each item
was tested on its own before being measured: every inlined primitive's
fallback (a bignum result, a flonum comparison, an error with the
builtin's wording), and a REPL `define` of `car` not being inlined.
Lambda groups were run under GC stress, since their closures are cyclic
by construction.

## Surprises

- The fused test-and-jump paid much less than its share of instructions.
  What's left of `fib`'s time is spread over the dispatch loop's handling
  of calls, and no single instruction stands out.
- D9's question, whether inlining is safe at a REPL, was answered by P8's
  rule that imported names get a fresh cell when redefined.
