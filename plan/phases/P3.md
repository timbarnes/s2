# P3. Garbage collection

Done 2026-10-10. The heap is collected by non-moving mark-sweep, adapted
from s1. A loop that allocates two pairs per iteration runs ten million
times in 5MB, where P2 needed 2.6GB.

## What was built

| File | Change |
|---|---|
| `heap.rs` | the collector: `needs_gc`, `collect`, the `Marker` (mark phase), sweep with optional poisoning; allocation counting; `S2_GC_STRESS` and `S2_GC_POISON` |
| `vm/machine.rs` | `safepoint`, called on entry to `Call` and `TailCall` |
| `globals.rs` | `Env::roots`: the binding cells |
| `main.rs` | GC tests; every result test now runs in stress and poison mode |

About 120 new lines of source, plus tests. The roadmap estimated 500,
which assumed more of s1's collector would carry over. Most of s1's
`gc/heap.rs` is ephemeron tables for its expander, which s2 doesn't have.

## Decisions

**D3: s1's design, unchanged in its essentials.**

- One `Box` per object and a list of all objects. Objects never move, so a
  `GcRef` held in Rust stays valid while the object is live.
- **Epoch marks.** `collect` bumps `epoch`; an object is marked when its
  `mark` equals it. Nothing needs to be unmarked afterwards.
- **An iterative worklist** (`Marker.grey`). An object is marked when it is
  *pushed*, not when it is popped, so an object reachable by many paths is
  traced once (s1 learned this the hard way).
- **The trace is one exhaustive `match`** with no `_` arm. When a later
  phase adds a kind of object (boxes in P4, continuations in P7), the
  compiler forces a decision about what it refers to.
- **Sweep** is `objects.retain`, freeing each unmarked object.

**Scheduling** (`needs_gc`): collect when the allocations since the last
collection exceed both a threshold (20,000, s1's default) and the number
of objects that survived the last collection. The second condition keeps
total marking work proportional to total allocation. With a fixed
interval, a computation whose live data keeps growing re-marks all of it
every interval, which is quadratic. The deep-recursion test checks this:
100,000 frames, each keeping a pair alive, mark 139,824 objects in
total; with a fixed interval it is 299,785, and the test fails.

**The root set** is passed by the VM to `Heap::collect` as an iterator of
values:

1. the value stack;
2. the closure saved in each frame;
3. the running closure (a register, a local of the dispatch loop);
4. the environment's binding cells, which reach every global's value;
5. the symbol table, added by the heap itself.

The symbol table is a root, not weak, as the roadmap suggested: the
simplest choice. Symbols are never freed. Making it weak needs only a
`retain` on `symbols` before the sweep, if it ever matters.

**Roots 2 and 3 are redundant, today.** A procedure's closure always sits
in its callee slot, `stack[fp - 1]`, for as long as it runs (03 §5's frame
layout; the top-level thunk is put in slot 0 by `Vm::run`). So the value
stack already reaches every frame's closure. I found this by removing the
frame roots to check that a test failed: none did. They are kept anyway,
since they cost one pass over the frames, and P7's continuations will
copy stacks around in ways that make the invariant easy to break.

**Safepoints: `Call` and `TailCall` entry only.** The roadmap also listed
"returning from a builtin". It isn't needed: every allocation happens in a
call (a builtin, a rest list) or in `MakeClosure`, and every loop is a tail
call, so the next safepoint is never far away. At call entry everything
live is on the stack: the callee, its arguments, and the caller's
temporaries. The check is one inlined comparison; `fib 30` went from
0.16s to 0.17s (medians of 11 interleaved runs), within noise.

**Nothing else needs rooting.** As 03 §4 planned: allocation never
collects, so the reader, expander and compiler can keep values in Rust
locals freely. A compiled template becomes reachable (from the closure
`Vm::run` pushes) before the first safepoint. Builtins don't call back
into the VM. The one VM primitive that allocates, `dis`, compiles and
prints, and keeps nothing.

**Debug modes** (03 §15), read from the environment by `Heap::new`, so
they reach the `s2` processes that the CLI, golden and differential tests
start:

- `S2_GC_STRESS`: collect at every safepoint.
- `S2_GC_POISON`: instead of freeing an object, overwrite it with the
  symbol `<<FREED>>` and leak it. A premature free then shows up as that
  symbol in output, or as a VM panic on a type it didn't expect, rather
  than as a use-after-free.

## Tests

`cargo test` runs 66 tests, all passing. New:

- **Every result test** (`run` in `main.rs`) now runs with stress and
  poison on, so all of P1 and P2's behaviour is checked with a collection
  at every call.
- **Objects reachable only through a closure** survive: a captured list,
  and a quoted constant in a lambda's template.
- **Flat memory:** a million iterations that each allocate two pairs, with
  the heap never holding more than one collection interval's worth of
  objects.
- **Linear collection time:** the deep recursion described above.
- **A unit test of `collect`**: a cycle and a string are freed; a list and
  the symbol table are kept.

The whole suite also passes with `S2_GC_STRESS=1 S2_GC_POISON=1 cargo
test`, in 8 seconds.

**Checking the checks.** Each was broken on purpose to see a test fail:

| Broken | Caught by |
|---|---|
| value stack not a root | most result tests (`<<FREED>>`, or a panic) |
| closures' free variables not traced | the new captured-list test; *no* test caught it before, since every earlier closure test captured fixnums |
| templates' constants not traced | the quoted-constant test (a VM panic) |
| fixed collection interval | the deep-recursion test |
| frames not roots | nothing: see "redundant" above |

## Measurements

Release build, `/usr/bin/time -l`:

| | P2 (no GC) | P3 |
|---|---|---|
| loop allocating 2 pairs × 10,000,000 | 1.36s, 2.6GB | 1.11s, 5MB |
| non-tail recursion 1,000,000 deep, a live pair per frame | 0.15s, 300MB | 0.18s, 305MB |
| `fib 30` | 0.16s | 0.17s |

- The allocating loop is *faster* with the collector: freed memory is
  reused by mimalloc while it is still in cache, instead of fresh pages
  being faulted in.
- The deep recursion's memory is its live data (a million pairs, frames and
  stack slots), so the collector can't reduce it; it costs 20% here
  because almost every object it marks survives.
- These `fib` times are about a quarter of P2's on the same command,
  so this machine is not the one P2 was measured on (or not in the same
  state). Only same-session comparisons mean anything.

**Against s1** (s1 rebuilt natively; the first run of this phase found
its binary was a Linux build, so the differential test had been skipping
itself). Interleaved runs, same session:

| | s1 | s2 | s1 / s2 |
|---|---|---|---|
| `fib 25` (`bench.sh 9`, medians) | 0.12s | 0.03s | 4.0x |
| `fib 30` (`bench.sh 9`, medians) | 1.27s | 0.36s | 3.5x |
| allocating loop, 10,000,000 × 2 pairs (3 runs each) | 5.64-5.75s, 5MB | 1.98-1.99s, 5MB | 2.9x |

- The `fib` ratios match P2's 3.3-4x, so the safepoint check costs nothing
  measurable against s1.
- Both collectors hold the allocating loop in the same 5MB. s2's time
  here (1.99s) is higher than in the table above (1.11s), which was an
  earlier session: the machine's drift again.
- The differential test passes, with and without `S2_GC_STRESS=1
  S2_GC_POISON=1`.

## Surprises

- How little of s1's collector was needed. The algorithm is about 60
  lines; s1's file is 778 because of its expander's side tables.
- The redundant frame roots, and the untested closure tracing: a stress
  mode only finds rooting bugs that some test exercises with a heap
  object in the right place.
