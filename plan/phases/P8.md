# P8. Libraries, `eval` and programs

Done 2026-10-11. s2 has `define-library`, `import` with all four import-set
forms, library files on a search path, `include`, `include-ci`,
`cond-expand`, `features`, first-class environments with `eval`, and
programs with `command-line` and `exit`. chibi's R7RS suite passes 1,154
tests: exactly s1's count, section by section. That was the roadmap's goal
for P9.

## Decisions

**Environments, as in s1** (`design/libraries-design.md`):

- **The system environment** has the builtins, the core forms and what
  `scheme/core.scm` defines. No user code runs in it. The standard
  libraries export its bindings.
- **The interaction environment**, where the REPL and programs run, starts
  with every system binding *imported*. `define` of an imported name gives
  it a fresh local cell (the system's is untouched, so `core.scm`'s `map`
  keeps using the real `car`), and `set!` of one is an error. That answers
  the roadmap's question about REPL redefinition: s1's rule.
- **Library environments** start empty and contain only what the library
  imports and defines. `environment` makes immutable ones.

An environment is a heap object, `Obj::Environment`, because `eval` takes
one as a value, and because macros need to name one (next).

**A macro remembers its definition environment.** In P5 there was one
top-level environment, so an alias's definition scope was just a depth.
With several environments, a macro imported from the system environment,
`when` say, expands into `if`, and in a library that never imported `if`,
that must still mean the system's `if`. So `SyntaxRules` and each alias
record their top-level environment as well as the depth, and resolution
moves to it when it follows an alias. A global then resolves to a binding
*in an environment*. Two globals are the same for literal matching if they
share a cell (an import shares the library's), or are both unbound and
named alike, which is how `else` in `cond` still works.

**Macros are exported and imported like variables.** An export table
maps names to bindings: a cell, a macro or a core form. Importing binds
the name to the same binding, marked imported. An exported macro expands,
through its aliases, into names in its library's environment, so it can
use the library's unexported helpers.

**Imports act during expansion.** `import` binds names when the form is
expanded, so the forms after it compile against them. `define-library`
does its work then too: it collects the declarations, imports into a new
environment, and expands the body there. The code produced runs with the
form and ends by calling `%register-library`, which checks every export
is defined and only then registers the library. So one whose body fails
isn't registered, as in s1.

**Loading a library file without running Scheme inside the expander.**
Compiling `(import (foo bar))` may need `foo/bar.sld` loaded first, which
means running Scheme in the middle of compiling. s1 handles this at run
time, by rewriting the `import`. s2 never runs code from inside the
expander, or the VM from inside the VM, so:

- the expander records the file (`pending_load`) and fails;
- its caller loads the file and expands the form again. At the top level,
  that is `Session::eval`, which runs `(%load-library "file")`.
  Inside `eval`, the VM turns the call into `(%load-then-eval "file" expr
  env)`, so the loading is ordinary Scheme code on the same VM.
- `%load-library` is Scheme: mark the file loaded (so a library that
  imports itself can't loop), read it, and `eval` each form.

**A pinned root.** While `Session::eval` loads a library file, the form
waiting to be expanded again is held only by Rust, and the load runs the
VM, which collects. The heap now has a list of pinned values for this.
The unit test `libraries_and_eval` imports a library file under GC stress
and poison. With the pin removed, the form comes back as `<<FREED>>`.

**`eval` is part of the call instruction**, like `apply` and `%call/cc`
in P7. It compiles the expression for its environment and calls the
resulting thunk in its own place, so `eval` in tail position is a tail
call (a new tail-context test). This was 03 §11's last candidate for an
`Action` type, which is now not needed at all.

**Errors found while compiling a form abort the form.** `set!` of an
imported name, `import` in a body, or a misplaced `cond-expand` `else`
are found when the top-level form is compiled. A `guard` in that same
form can't catch them, since the form never runs. s1 finds them at run
time. Through `eval`, they are raised like any other error, so s1's tests
of them are ported as calls to `eval`.

**Programs** (R7RS §5.1): `s2 PROGRAM ARG ...` runs the file's forms in
order in the interaction environment, and the first error ends it with
status 70, as in s1. `(command-line)` is the program and its arguments. A
first line starting `#!` is skipped, so a program can be a script. The
old behaviour of `s2 FILE`, which reports an error and goes on to the next
form, is now `s2 -f FILE`. The conformance runner uses it.

**`exit`** is Scheme: it leaves every `dynamic-wind` (running the after
thunks, as R7RS requires), then calls `%exit`. `emergency-exit` calls
`%exit` directly.

**Library files** are found as `foo/bar.sld` in the directories of
`S2_LIBRARY_PATH`, then `.`, then `<prefix>/share/s2/lib`. s1 also looks in
the user's data directory, through the `dirs` crate. That is marked
`ponytail:`, to add if anyone installs libraries per user. Relative
`include` names in a library file are relative to its directory.

**`(s2)`** exports every system binding no standard library exports:
s2's own procedures, such as `dis` and `%frame-depth`.

**Not yet:** the auxiliary syntax `else`, `=>`, `_` and `...` isn't bound,
so `(scheme base)` can't export it, and nor is `syntax-error` (both P9).
The complex-number procedures aren't planned. A test lists exactly these
names as missing.

## Tests

`cargo test` runs 102 tests, all passing, and all also pass with
`S2_GC_STRESS=1 S2_GC_POISON=1`.

- **chibi's R7RS suite: 1,154 passing** (P7: 1,140), now with the suite's
  own `import` header. 6.12 passes 4 of 4 and 6.14 13 of 13. Every section
  equals s1's baseline. The 74 unreached tests are complex numbers, as in
  s1.
- **s1's `library_tests.scm`** (76 tests), with its `.sld` fixtures in
  `tests/libs`:
  - `eval`, `environment`, `load`;
  - imports shared with the library, `set!` and `define` of imported
    names;
  - import sets;
  - `define-library` with exported macros and unexported helpers,
    failing bodies, clashing imports, `include` and
    `include-library-declarations`;
  - library files found on the path, loading the libraries they import,
    loaded once;
  - `cond-expand` and `features`.

  The adaptations are listed at the top of the file.
- **s1's `process.rs`** (11 tests): exit statuses, `exit` running after
  thunks innermost first, `emergency-exit` skipping them, `command-line`,
  shebang lines, and errors ending a program with status 70.
- **Unit tests** (with GC stress): a library file imported while the GC
  runs, immutable environments, imported variables, `import` in a body,
  `eval` as a tail call.
- P6's test that calls every builtin with bad arguments passed it the
  string `"ab"`. That included `open-output-file`, which created a file
  `ab` in the working directory, and only a later call to `delete-file`
  with the same string removed it. Its string is now a path under
  `target/`.
