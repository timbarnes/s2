# P7. Continuations and dynamic control

Done 2026-10-10. s2 has re-entrant `call/cc`, `dynamic-wind`, multiple
values, exceptions (`with-exception-handler`, `raise`,
`raise-continuable`, `error`, `guard`), parameters and promises. Errors
from builtins and from the VM are raised, so `guard` catches them, and an
uncaught error prints its message, irritants and a backtrace. chibi's
R7RS suite passes 1,140 tests, against s1's 1,154. Every remaining
difference is in 6.12 (`eval`) and 6.14 (the system interface), which
are P8.

## Decisions

**D8: copy the stacks on capture**, as planned (03 §10).

- `%call/cc` copies the value stack and the frame stack into a
  `Continuation`. For a non-tail call, the running procedure's registers
  are put on top as the frame to return into. For a tail call, its
  caller's frame is the top one, as a tail call requires.
- Calling the continuation copies both stacks back and returns its
  argument (or a values object, for any other number of arguments) to the
  top frame. With no frames, the top-level form is finished.
- This also works across top-level forms: a continuation captured in one
  form and called from a later one runs the old form to its end, and that
  becomes the current form's value. s1 does the same, and s1's re-entrant
  `dynamic-wind` test relies on it.
- Measured, copying is cheap. Capturing a continuation 1,000 frames deep,
  2,000 times, is 4.2x faster than s1, whose capture is O(1). A segmented
  stack (03 §10's upgrade path) isn't needed on this evidence.

**Escape-only continuations** (`%call/ec`) record the stack heights and
the frame to return into. Calling one cuts the stacks back, if that frame
is still at its place on the frame stack; otherwise it is an error
(`escape continuation invoked after its extent has ended`). The check is by
the frame's contents, not by which top-level form made it, because a
guard's body can be re-entered from a later form (s1's "guard returns
normally after its body is re-entered" test).

**D9: control primitives are part of the call instructions, not
`Action`s.** 03 §11 planned VM primitives that return an `Action`
(return, tail-call, resume). In the event, `apply`, `%call/cc` and
`%call/ec` all just rearrange the stack before the same call dispatch.
P6 found this for `apply`, and the continuations work the same way.
Calling a `Continuation` or `Escape` object is one more case of that
dispatch. So `PrimFn` gained three variants that the call instruction
carries out, and there is no `Action` type. `eval` (P8) is the only
remaining candidate for one.

**Multiple values** are s1's: `values` returns one value as itself, and
any other number as a `Values` object, which `call-with-values` spreads
with `apply`. The REPL prints several values one per line.
`call-with-values` is three lines of Scheme.

**Dynamic control is Scheme** (03 §10), on `%call/cc` and `%call/ec`:

- `dynamic-wind` keeps the wind list `%winders`. The user's `call/cc`
  wraps the raw continuation in a procedure that winds from the current
  list to the saved one (after thunks out, before thunks in) and then
  calls it.
- **Exception handlers are not kept with `dynamic-wind`.** They are a list,
  `%handlers`, which continuation wrappers save and restore along with
  the wind list. Installing a handler runs no code, so it needs no
  winding, and crossing it costs nothing. That matters for `guard`,
  below.
- `raise` calls the innermost handler with the outer ones installed. If
  the handler returns, it raises a secondary error, `exception handler
  returned from a non-continuable raise of`, with s1's wording.
  `raise-continuable` returns the handler's value.
- An uncaught raise leaves every `dynamic-wind` (running the after thunks,
  as returning to the top level would) and then calls `%abort`, which ends
  the form. s1's test that an uncaught error runs the after thunks passes.

**`guard` costs constant time per guard.** R7RS's reference
implementation captures a full continuation on entry, and another to
re-raise from the right place when no clause applies. s1 uses it, and
with s1's heap frames each capture is O(1). With copied stacks each would
be O(depth), making s1's test of guards nested 8,000 deep quadratic. s2's
`guard` instead:

- runs the body under an escape-only continuation, which costs nothing;
- when something is raised, puts the guard's dynamic environment in place
  (its winders and handlers) and evaluates the clause *tests* inside the
  handler;
- escapes to the guard only if a clause applies, and runs that clause's
  body there, in the guard's continuation;
- otherwise puts the raise's dynamic environment back and re-raises with
  `raise-continuable`, right there, which is what the reference
  implementation achieves by re-entering the raise.

The one difference from the reference implementation is where the clause
tests run: in the right dynamic environment, but deeper on the stack. That
is visible only if a clause test captures a continuation. The unit test
`nested_guards_are_linear` checks the property that matters: guards
nested 8,000 deep, returning normally and re-raising through every level,
make no full continuation captures at all.

**Errors are raised.** When a builtin fails, or an instruction does (an
unbound variable, a non-procedure, a wrong argument count, a reference
before initialisation), the VM makes an error object and calls the Scheme
procedure `%raise-error` with it. To do that, it pushes the current frame
and enters the procedure as if the failing instruction had been that
call. `raise` never returns, so that frame is only ever seen by the
backtrace. `%raise-error` is a private name, so a program that redefines
`raise` doesn't capture builtin errors. Before `core.scm` has defined
`%raise-error`, an error just aborts the form, as before P7.

**Builtins return a typed `Error`** (kind, message, irritants), as 03 §11
planned. P6 deferred this, and P7 needed it: a file error must say it is
one (`file-error?`), and name the file as its irritant. `From<String>` and
`From<&str>` keep every existing `?` and `.into()` working, and an `err!`
macro replaces `format!` at the error sites. The VM's own errors are
strings, converted the same way.

**Uncaught errors** print as before, so every earlier test still passes:
the message, then the irritants written. Any other raised object prints
as `uncaught exception: boom`. After the message comes a backtrace: the
names of the procedures waiting in the frame stack, innermost first,
without anonymous ones or the exception machinery's. Tail calls leave no
frames, so it is the chain of non-tail calls.

```
s2> (define (f x) (car x)) (define (g x) (+ 1 (f x))) (g 5)
error: car: expected a pair, got 5
  in f
  in g
```

**Parameters** are s1's (`make-parameter` and `parameterize` over
`dynamic-wind`). `current-input-port` and friends speak the same
protocol as parameter objects, so `parameterize` rebinds them, and
`with-input-from-file` and `with-output-to-file` are s1's Scheme.

**Promises, `let-values`, `let*-values`, `define-values`** are s1's
Scheme, unchanged. **`case-lambda`** is new: a macro that counts the
arguments and applies the first clause that fits. No phase had listed it,
and chibi's 4.2 section and s1's tail tests both need it.

## A P4 design error

P4 boxed a `set!` variable only if a closure also captured it, and kept
the others in stack slots, written by `LocalSet`. That was right until
continuations could be re-entered. A continuation copies the stack, so
re-entering one restored those slots to their values at capture time. In
s1's first `call_cc_tests.scm` test, a loop variable `log` came back empty
after every re-entry, and a counter `n` never advanced, so the loop never
ended. Variables are locations, not values, and every copy must see the
same location. Since P7, every `set!` variable is boxed. This is the
assignment conversion of Dybvig's stack model, which boxes for exactly
this reason.

`letrec` variables that only their init assigns stay unboxed: re-entering
a continuation captured during a later init repeats the inits after it, so
a copied slot is still right. `tests/golden/set.dis` shows the change, and
P4's note has a pointer here.

## A P5 bug

In a top-level `begin`, a definition introduced by a macro (keyed by its
alias, so hidden) couldn't be referred to by a form *before* it in the
same `begin`. Until its cell existed, the alias resolved to the plain
global, which was unbound. chibi's 4.3 test of `(begin (define-syntax
ffoo …) (ffoo ff) (ff 10))` found it. A top-level `begin` now makes the
cells of its definitions before expanding any of its forms.

## Tests

`cargo test` runs 90 tests, all passing, and all also pass with
`S2_GC_STRESS=1 S2_GC_POISON=1` (unit tests 6 minutes, the differential
test 3½, the Scheme files 30 seconds).

- **chibi's R7RS suite: 1,140 passing** (P6: 880). The shim now has s1's
  `guard`-based `test`, `test-assert` and `test-error`, so a test that
  raises no longer aborts its form. Every section now equals s1's
  baseline except 6.12 (0 of 4) and 6.14 (3 of 13).
- **s1's Scheme test files**, in `tests/scheme/`, now all ported in full,
  apart from s1's extensions:
  - `call_cc_tests.scm` (9): multi-shot re-entry, re-entry 1,000 frames
    deep, 100,000 re-entries in bounded space, interleaved generators,
    `amb`, re-entry through `map`;
  - `exception_tests.scm` (37), with guards nested 8,000 deep;
  - `control_tests.scm` (11), s1's `dynamic-wind` tests, including
    re-entry from a later top-level form;
  - `data_tests.scm` (66 of 66) and `port_tests.scm` (36). The tests P6
    left out (guard, parameters, promises, `with-*-file`) are back.
- **Unit tests**:
  - continuations: escapes, re-entry, values, an escape used too late;
  - exceptions: builtin and VM errors caught by `guard`, file and read
    errors, uncaught messages, after thunks on an uncaught error,
    `raise-continuable`;
  - the backtrace;
  - nested guards making no full captures (via the VM's capture
    counter);
  - all 31 of s1's tail contexts.
- **Smaller sizes under stress.** `tests/scheme.rs` caps `test-size` at
  200 under GC stress, where every call collects and every collection
  marks the whole (deep) stack, as s1 does for its stress run. Without
  this, the 8,000-deep guards and 100,000 re-entries took hours.
- The unit tests' tail-context loops went from 500 to 100 iterations: 31
  contexts under stress had made them the slowest test (10 seconds).

## Measurements

Release build, interleaved runs, medians; load average about 3.5.

| | | | |
|---|---|---|---|
| `fib 30`, P6 vs P7 (9 runs) | 0.15s | 0.15s | unchanged |
| `fib 30`, s1 vs s2 (`bench.sh 7`) | 0.60s | 0.15s | 4.0x |
| generator over 100,000 elements, s1 vs s2 (5 runs) | 0.26s | 0.10s | 2.6x |
| 100,000 raises caught by `guard` | 0.30s | 0.07s | 4.3x |
| `call/cc` captured 1,000 frames deep, 2,000 times | 0.50s | 0.12s | 4.2x |

- The generator captures two continuations and re-enters two per element,
  at shallow depth: the common use of re-entry.
- The deep capture is the case copying should be worst at. It is still
  faster than s1's O(1) capture, because copying 1,000 frames is one
  `memcpy`, and s1 pays for its heap frames on every call.
- Unifying `Call` and `TailCall` into one arm cost nothing measurable on
  `fib`.

## Surprises

- The P4 boxing error. It only shows when a continuation is re-entered,
  so no test could find it before P7.
- Copying the stacks is fast enough that the segmented stack, planned as
  P10's fallback, may not be needed.
- `Action` wasn't needed. Every control primitive turned out to be a
  rearrangement of the stack before an ordinary call.
- Handlers kept out of the wind list are what makes `guard` linear. With
  `with-exception-handler` built on `dynamic-wind`, each re-raise would
  unwind and rewind every handler in between.
