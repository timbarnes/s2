# P5. The macro expander

Done 2026-10-10. The minimal expander is replaced by one with a syntactic
environment and hygienic `syntax-rules`. `cond`, `case`, `and`, `or`,
`when`, `unless`, `let*` and `do` are macros in `scheme/core.scm`.

```
$ s2 --expand -e "(define (f x) (or x 'none))"
(define f (named-lambda (f x.1) (let ((x.2 x.1)) (if x.2 x.2 'none))))
```

`or`'s temporary is called `x` in core.scm, the same name as the user's
parameter. The two are different variables, `x.2` and `x.1`.

About 750 new lines of Rust, 540 forked and 75 of Scheme, plus tests. The
roadmap estimated 1,500 new and 1,300 forked. s1 needed more because its
aliases resolve against runtime environments (with an ephemeron table for
the GC) and its literal data is stripped in a separate pass. s2 needs
neither, as described below.

## Decisions

**D10: hygiene by renaming, resolved at expansion time** (03 §12).

- **Aliases.** Expanding a use renames every identifier its template
  introduces to an alias, a new heap object `Obj::Alias { original,
  depth }`: one alias per identifier per expansion.
- **Resolution** (`resolve_in`): look the identifier up in the visible
  frames, innermost first, then in the top-level environment. If it is
  found nowhere and it is an alias, look up its original in the macro's
  definition scope instead. That is all of hygiene:
  - a binding the expansion makes (`(let ((temp e1)) …)`) binds the alias
    itself, which no user code can name;
  - a free identifier in a template (`if`, `memv`) is found nowhere as an
    alias, so it means what it meant where the macro was defined.
- **The definition scope is a depth,** the number of frames visible where
  the macro was defined, not an environment object. Frames are a stack, so
  while a macro is in scope, the frames below that depth are the same
  ones. s1 needs an `EnvRef` and keeps it alive through an ephemeron table.
  In s2 the depth is just a number, and a top-level macro has depth 0.
- **Literals** match by `free-identifier=?`: the literal, resolved in the
  definition scope, and the input identifier, resolved at the use, must
  give the same `Binding`. So `(let ((=> #f)) (cond (#t => 'ok)))` is `ok`:
  the local `=>` is a variable, not `cond`'s literal.
- **Quoted data** is turned back into plain symbols when the expander meets
  `quote`, a quasiquote's constant parts, or a vector constant. s1
  needed a separate walk over each expansion, because it doesn't expand
  ahead of evaluation.

**Introduced top-level definitions are hidden, as in s1.** `(define
march-hare 42)` in a template binds the *alias* in the top-level
environment, which is therefore keyed by identifier rather than symbol. The
macro the same expansion defines finds it, and user code doesn't, which
is what s1's `jabberwocky` test checks.

**Core forms and macros are bindings.** The top-level environment maps
each identifier to a `TopBinding`: a variable's cell, a macro, or a core
form. So:

- `(define if …)` redefines `if` as a variable, and a later `(if 5)` is a
  call;
- a local variable named like a keyword shadows it, as in P2, but now
  through the same lookup as everything else;
- the expander dispatches on bindings, not names.

The core forms are `quote`, `quasiquote`, `unquote`,
`unquote-splicing`, `lambda`, `define`, `set!`, `if`, `begin`, `let` (and
named `let`), `letrec`, `letrec*`, `define-syntax`, `let-syntax`,
`letrec-syntax` and `syntax-rules`.

**Which forms are Rust and which are macros.** The Rust cases are the ones
the core AST needs, plus `quasiquote`. The roadmap put `letrec` and
`letrec*` in `core.scm`, but they *are* the core `Letrec` node, so they
stayed Rust cases.

**`core.scm` is compiled in** (`include_str!`, as s1 does) and evaluated
when a session starts, which costs 0.2ms (2.5ms to 2.7ms for `s2 -e 1`).
It holds `and`, `or`, `when`, `unless`, `let*`, `cond` (with `=>`), `case`
(with `=>`) and `do`, mostly from R7RS §7.3. `let-values`, `let*-values`
and `define-values` are not there yet: they need `call-with-values`, so
they move to P7.

**Body rules** (R7RS §5.3.2), in two passes:

1. Expand each form's head until it is known to be a definition or not (a
   macro use may expand into one); splice `begin`s; bind each `define` and
   `define-syntax` in the body's frame; stop at the first expression.
2. Expand the definitions' values and the expressions, with every
   definition in scope.

So a macro defined in a body can refer to a procedure defined after it
(s1's "forward reference" test). The definitions become a `Letrec`, as in
P4.

**`let-syntax` bodies are bodies**, so definitions in them are local, as in
s1.

**Quasiquote** is expanded in Rust into calls to `cons`, `append` and
`list->vector`, with nesting levels, and constant parts left as constants.
The calls go through the global cells of those three procedures, so a
program that redefines `cons` globally changes quasiquote. This is marked
`ponytail:`, to fix with private primitives if it ever matters.

**Differences from s1, all from expanding at compile time.** 03 §12
predicted these:

- **A macro used before its definition is an error.** In `(define (f) (m))`
  followed by `(define-syntax m …)`, `(m)` was compiled as a call, so
  `(f)` fails with `unbound variable: m`. s1 expands lazily, and gives 1.
- **Redefining a macro doesn't change code already compiled.** s1's
  expansion-cache test (`which-version`) expects the new definition to be
  used; s2 keeps the old expansion. This is how compiling Schemes behave.

## Two problems found by testing

**Stack depth.** The expander, analysis and code generation all recurse
over the code, and macros turn long argument lists into deep nesting: an
`or` of n arguments is n nested `let`s.

- On a 2MB thread stack (Rust's default for test threads), a debug build
  overflowed between 100 and 200 nested uses of `my-or`, a release build
  between 400 and 800.
- `main` now runs the session on a thread with a 1GB stack. That is
  address space, committed only as deep as the code actually goes.
  `.cargo/config.toml` sets `RUST_MIN_STACK` so test threads get the same.
  3,200 nested uses then work in a debug build.
- A macro that expands forever is now an error after 10,000 nested
  expansions (`macro uses nested more than 10000 deep: …`) instead of a
  stack overflow that kills the process. I found this by writing a test
  whose two `letrec-syntax` macros expanded into each other forever.

**Expansion time was O(n³) in the length of an ellipsis match.**
Instantiating `sub ...` copied the whole bindings map once per
repetition, including each matched sequence. Expanding a recursive macro
like `or` with n arguments therefore took O(n³) time: a 3,000-argument
`or` made the unit tests take 146 seconds in a debug build. s1's code has the same
cost. The sequences are now shared (`Rc<[Match]>`), so a copy is cheap,
and the whole expansion is O(n²) (the matched list is re-walked at each
level): 0.35s for 3,000 arguments in a release build.

## Tests

`cargo test` runs 82 tests, all passing, and all also pass with
`S2_GC_STRESS=1 S2_GC_POISON=1`. That run now takes 76 seconds, because
each collection also marks `core.scm`'s macros.

- **Hygiene** (`hygiene`, `macro_defining_macros_and_scope`), from s1's
  `syntax_rules_tests.scm`:
  - `swap!` with a user `tmp`; `my-if` under local `else` and `cond`;
  - free identifiers seen from the definition scope; a local `if` around
    `when`;
  - `my-or` with shadowed `let`, `if` and `temp`;
  - literals bound at the use site; `set!` through an alias;
  - quoted template data; quasiquote in a template;
  - macro-defining macros with `(... ...)` and with a custom ellipsis;
  - the hidden introduced definition; internal `define-syntax`;
    `let-syntax` scoping; the forward reference; begin splicing;
    `letrec-syntax`; redefining a macro or a core form as a variable.
- **Matcher unit tests** in `syntax_rules.rs`:
  - a middle ellipsis, dotted tails, vectors, nested ellipses and `_`;
  - literals and escapes, custom ellipses;
  - validation errors, alias identity, and `strip_datum`.
- **Derived forms, quasiquote and errors:**
  - every form in `core.scm`, including `do` with a user variable named
    `loop`;
  - quasiquote nesting, splicing and vectors;
  - "no syntax rule matches", malformed rules, syntax used as a variable;
  - deep and infinite expansions.
- **Tail contexts:** 16 more from s1's `tail_tests.scm`: `cond` (and
  `=>`), `case` (with `else` and `=>`), `and`, `or`, `when`, `unless`,
  `let*`, `let-syntax`, `letrec-syntax`, `do`'s result, and a macro use.
  The ones still missing need `let-values`, `case-lambda`, `apply`,
  `call/cc` or `call-with-values`.
- **`--expand`:** a unit test of `show`, and a CLI test.
- **Golden:** `macros`. It shows that `my-or` leaves no trace in the
  compiled code: its recursive use is a plain `TailCall`.
- **Differential:** `tests/diff/p5-macros.scm` gives the same output as
  s1. It leaves out `(when #f 1)`: s2 displays the unspecified value as
  nothing (a P1 printer choice), and s1 as `#<undefined>`.

**Not ported from s1's macro tests**, because they need later phases:

- `guard` and error objects (the error cases);
- s1's procedural `macro`, which is left out by design;
- `(gc)` (stress mode covers it);
- `syntax-error` and auxiliary syntax bindings (P9);
- `import` (P8);
- the expansion cache (see above).

## Measurements

Release build, interleaved runs, medians. The machine was idle (load 3-4).

| | | | |
|---|---|---|---|
| `fib 30`, P4 vs P5 (9 runs) | 0.17s | 0.16s | unchanged |
| `s2 -e 1`, P4 vs P5 (100 runs) | 2.5ms | 2.7ms | `core.scm` costs 0.2ms |
| a `do` loop using `cond`, `and` and `or`, 1,000,000 iterations, s1 vs s2 (7 runs) | 0.55s | 0.12s | 4.6x |

The macro loop's ratio is higher than `fib`'s 3.6x. Macros cost s2 nothing
at run time, since they are gone before code generation. s1 looks up its
expansion cache at every evaluation of a use.

## Surprises

- How much simpler hygiene is in an expander than in an interpreter.
  Resolution happens once per identifier, so a definition scope can be a
  depth, and no GC-aware side tables are needed.
- The O(n³) expansion, inherited from s1. It was invisible at the sizes
  s1's tests use.
- Stack depth, which a tree-walking compiler has and a CEK machine
  doesn't.
