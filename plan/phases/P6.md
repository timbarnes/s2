# P6. Data types and builtins

Done 2026-10-10. s2 has R7RS's data types and their procedures, except the
control features: the numeric tower, characters, strings, symbols, lists,
vectors, bytevectors, records and ports. On chibi's R7RS suite, every
section this phase covers passes all its tests except those that need P7
(`guard`, `values`, `call-with-values`) or complex numbers.

## What was built

| File | Change |
|---|---|
| `builtins/` | was `builtins.rs`; now one module per R7RS chapter, forked from s1's `builtin/*` and `ports.rs` |
| `builtins/number.rs` | the numeric tower (fixnum, bignum, exact rational, flonum), with a fixnum fast path |
| `builtins/{predicate,list,char,string,vector,record,port}.rs` | the rest of s1's builtins, about 250 procedures in all |
| `heap.rs` | `Obj::Port`, `Obj::RecordType`, `Obj::Record`; a cycle-safe `equal` (from s1) |
| `io.rs` | an output file port owns its `File` (s1's file table is gone) |
| `vm/machine.rs` | `apply`; the current ports (`Vm::ports`), which are GC roots |
| `printer.rs` | ports and records, printed as in s1 |
| `scheme/core.scm` | `define-record-type`, `map`, `for-each`, `member`, `assoc`, `string-map`, `vector-map` and the rest, `call-with-port` and the `call-with-*-file`s |
| `tests/r7rs/` | chibi's suite, the runner (forked from s1) and a temporary `syntax-rules` shim |
| `tests/scheme/` | s1's `data_tests.scm` and `port_tests.scm`, ported, with a small harness |

`src/builtins/` is 1,900 lines, two thirds of them forked. The roadmap
estimated 5,000 forked and 1,000 new. The s1 code shrank in the port:

- each s1 builtin checks its own argument count and registers a docstring
  for `help` (an s1 extra). In s2, one table gives each procedure's
  arity, which the VM checks;
- argument checking (`string_arg`, `index_arg`, `range_args`, …) is shared
  across modules;
- s1's unit tests of single builtins are replaced by the Scheme test files
  and a test that calls every builtin with bad arguments (below).

## Decisions

**Builtins are tables of `Primitive`s with exact arities.** Each module
exports `PRIMITIVES`, and `builtins::install` binds them all. A wrong
argument count is reported by the VM, uniformly:
`string-ref: wrong number of arguments: 3`. Type errors use s1's wording
(`car: expected a pair, got 1`), so P1's messages changed to match.

**The numeric tower** is s1's code over s2's representation:

- fixnums (61 bits) and flonums are in the `Value`; bignums and exact
  rationals are heap objects;
- every integer that fits is a fixnum (`Heap::integer`), so `eqv?` on
  integers is simple;
- arithmetic on anything other than fixnums goes through s1's `Num` enum
  and back.

The fixnum fast path covers `+ - *`, the comparisons and the integer
divisions. When every argument is a fixnum, they compute in `i128` (or
`checked_mul`) and allocate nothing; overflow falls back to bignums.
`fib 30` even got a little faster than with P5's fixnum-only arithmetic
(0.16s to 0.14s, medians of 9). I haven't looked into why.

**Rust versus Scheme.** A builtin can't call a procedure (it never
re-enters the VM, 03 §11). So everything that takes a procedure argument
is written in Scheme in `core.scm`, as in s1: `map`, `for-each`,
`member` and `assoc` with a predicate, the string and vector mappers,
`call-with-port`. Everything else is Rust, including the `cxr`s, which s1
wrote in Scheme.

**`apply` is part of the VM's call instruction.** `Call` and `TailCall`
see the primitive `apply`, spread its last argument onto the stack, and
call the procedure as if the call had been written out. So `(apply f
args)` in tail position is a tail call to `f`; the `apply` tail context
from s1's `tail_tests.scm` now passes. The roadmap put `apply` in P7, with
`Action`, but multi-list `map` needs it now, and this is simpler: no
re-entry, just a different stack layout before the same call.

**Ports** are `Obj::Port(RefCell<PortKind>)`, with s1's `PortKind`.

- The current input, output and error ports are three values in the VM,
  so the procedures that default to them are VM primitives.
- An output file port owns its `File`, so closing the port, or collecting
  it, closes the file. s1 kept files in a table indexed by port.
- File output is unbuffered, so nothing is lost if a program exits
  without closing its port.
- `parameterize` on the current ports, and `with-input-from-file` and
  `with-output-to-file` (which need it), come with parameters in P7.

**Records** are s1's: a `define-record-type` macro over five
primitives, and record and record-type heap objects. An accessor finds its
field by name on every call, as in s1. That is marked `ponytail:`, to
compute the index once if P10 shows it matters.

**`equal?` terminates on cyclic data** (from s1): after 10,000 steps it
starts recording the node pairs being compared.

## Deferred to P7

- **Error objects.** The roadmap said builtin errors would "become proper
  error objects" here. But nothing can catch or inspect an error object
  until `raise` and `guard` exist, so an error object made now couldn't be
  observed. Builtins still return error strings, and P7 turns them into
  raised error objects in one place, the VM's handling of `Err`.
- **`floor/`, `truncate/`, `exact-integer-sqrt`**, which return multiple
  values.
- `read-error?`, `file-error?`, parameters, and `with-*-file`.

## Not ported: s1's extras

`type-of`, `procedure-source`, `void`, `shell`, `add-doc`, `gc-threshold`,
`>string`, `push-port!` and `pop-port!` are s1 extensions, left out as
planned.

One s1 behaviour is deliberately different. s1 names an anonymous closure
after the first variable it is `define`d to: `(define add1 (adder 1))`
prints as `#<procedure add1>`. s2 names procedures when they are compiled
(P2), and the name lives in the template, shared by every closure made
from that `lambda`. Doing what s1 does would need a name slot in every
closure, just for printing.

## Tests

`cargo test` runs 86 tests, all passing, and all also pass with
`S2_GC_STRESS=1 S2_GC_POISON=1` (about 4 minutes now, because the
standard environment is bigger and stress mode marks it all at every
call).

- **chibi's R7RS suite** (`tests/r7rs/run.sh`, baseline recorded):

  | section | s2 | s1 |
  |---|---|---|
  | 6.1 Equivalence, 6.3 Booleans, 6.5 Symbols | 25, 18, 17 | the same |
  | 6.6 Characters, 6.7 Strings | 79, 130 | the same |
  | 6.8 Vectors, 6.9 Bytevectors | 43, 39 | the same |
  | 6.2 Numbers | 183 | 194 |
  | 6.4 Lists | 59 | 65 |
  | 6.13 Input and output | 61 | 63 |

  Every shortfall is a test that uses `call-with-values` or `values` (11
  in 6.2, 1 in 6.4, plus the tests after it in its form) or `guard` (2 in
  6.13). No test in these sections fails. 880 tests pass across the whole
  suite, against s1's 1,154; most of the gap is P7's control features and
  P8's libraries.
- **The temporary shim** (`tests/r7rs/shim.scm`) is s1's, rewritten with
  `syntax-rules` and without `guard`. An error aborts its top-level form,
  and the test is counted as an error when the next one starts. So
  `test-error` tests count as errors until P7 gives the shim `guard`. The
  suite's `import` header isn't run until P8.
- **s1's `data_tests.scm` and `port_tests.scm`** (`tests/scheme/`, run by
  `tests/scheme.rs`): 59 of 66 and 30 of 42 tests ported. The ones left
  out need `guard`, promises, parameters, or s1's extras. The list is at
  the top of each file.
- **No builtin panics on bad arguments**: a unit test calls every
  primitive with every allowed number of arguments, each drawn from
  fourteen values of different types (thousands of calls). The ported code
  replaced s1's per-function arity checks with the table's, and this test
  makes sure no function relied on a check it no longer gets.
- **Unit tests** (with GC stress, as every `check` is): `apply`, including
  errors and the multi-list mappers built on it; records, string ports,
  rationals, bignums and integer division.
- Two older tests got smaller (`fib 20` to `fib 15`, `parity` 10,000 to
  1,000): with GC stress, each collection now marks the larger standard
  environment, and the unit tests had grown to 7 seconds.

## Measurements

Release build, interleaved runs, medians; load average about 4.

| | | | |
|---|---|---|---|
| `fib 30`, P5 vs P6 (9 runs) | 0.16s | 0.14s | faster |
| `fib 30`, s1 vs s2 (`bench.sh 7`) | 0.60s | 0.15s | 4.0x |
| lists and strings, s1 vs s2 (7 runs) | 0.75s | 0.23s | 3.3x |

The lists-and-strings workload does `(apply + (map square (iota 10000)))`
100 times, then `string-append` of 200,000 `number->string`s. It is the
first measurement that isn't dominated by calls and fixnum arithmetic.
That its ratio is a little lower than `fib`'s is no surprise: the work
inside a builtin (allocating, copying strings) is much the same in both
systems.

## Surprises

- How much smaller the forked code became. s1's builtins were written
  before it had shared helpers, and each one did its own checks.
- `apply` belongs in the call instruction, not in a builtin calling back.
  It needs no new mechanism.
